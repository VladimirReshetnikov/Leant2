conditional theorems, bounded algorithms, counterexamples, native API
directions, and experimental protocols. Those questions are no longer the
active agenda. Sections~\ref{sec:search}--\ref{sec:learning} contain the
\emph{33 replacement questions}, identified by R1.N1--R9.N3; this section
sets priorities and preparation requirements without repeating their wording.
An answer establishing a finite model or a restricted theorem does not settle
its unrestricted extension or demonstrate a useful implementation.

\paragraph{Preparation order.}
First establish the P0 interfaces of Section~\ref{sec:roadmap}: the frozen
query, permitted axioms, completion semantics, publication contract and
separate result statuses. Then prepare R3's smallest useful certified
observation fragment, R4's native adapter and R5's realization/publication
boundary alongside R1's effect and replay examples. These decide interfaces
that would otherwise be expensive to revise. R2's finite carrier checker and
bounded package enumeration can proceed immediately; they do not wait for
unrestricted minimal-carrier or automatic invariant invention results.

R6 and R7 should share the same dependency and context identities. Their
experiments can proceed once those identities are stable. Freeze R8's
objective before claiming search optimality or evaluating learning; defer
R9's benefit claim until a paired native baseline and the carrier/helper
oracle exist. This order follows implementation dependencies, not a claim
that one research topic is intrinsically more important.

\paragraph{What counts as a useful response.}
For a semantic question, request a theorem with explicit grammar, scope,
axiom, termination and completeness hypotheses, or a counterexample to the
proposed boundary. For a native interface question, request a minimal
reproducible example pinned to the actual Lean version, including failure
and rollback. For an empirical question, agree on a decision-changing
comparison before collecting results: held-out tasks, matching work and
deadline budgets, cold/warm cost, and all certification/publication stages.
An external benchmark or submitted Python model is a starting artifact,
not a Leant2 acceptance result.

\paragraph{Contact and ownership.}
The cited projects and the Lean community are possible discussion venues;
this agenda records no outreach or endorsement. The artifacts above are
preparation tasks unless a repository receipt explicitly establishes that
they exist. The engineering and adaptation items also require specialist
review where they cross compiler, contextual-refutation or parametricity
boundaries. Their classification is not evidence that every implementation
detail is already solved.
