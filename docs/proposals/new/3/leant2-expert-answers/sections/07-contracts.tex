\section{R6: contracts beyond finite decidable observations}
\label{sec:contracts}

\Q{R6.1}{How should value and proof holes be interleaved without an SMT solver?}
\ans Use a dependency-aware scheduler with proof obligations at stable interfaces. Lean propositions do not require an SMT solver to play the role of refinements, but unrestricted proof search is not a cheap substitute for liquid inference. Restrict the first abstraction and prove its transfer rules.

There are three useful stages. During value construction, propagate cheap, proved abstract facts about shape, length, bounds, or membership. Once the value choices on which a local obligation depends are fixed, attempt the local proof with the branch induction hypotheses. After all branch values and local proofs are available, prove any remaining global property of the assembled program. A failure at one proof tier returns a pending obligation, not a refutation.

The proposal says that proof search about a program with holes is not meaningful before those holes are filled. That is too strong. A lemma may establish a property uniformly in a still-unknown component; a branch invariant may characterize all allowed fillings. What is unsafe is letting a failed speculative proof attempt exclude every future filling without justification. Use metavariables as existential construction choices, and explicit binders or interface assumptions when reasoning universally about all future choices.

A non-SMT analogue of liquid abstraction is a finite family of predicates with Lean-proved implication and transfer rules. For instance, abstract a list result by empty/nonempty status and a symbolic length expression. A component signature can carry a theorem saying how it transforms these facts. Abstract conjunction and implication checks reduce to a finite table or small certified procedures; \code{simp} and \code{omega} discharge the remaining arithmetic leaves. Synquid is a relevant precedent for refinement-guided synthesis, but its solver-supported refinement discipline is not already an implementation of arbitrary Lean proposition search \cite{synquid}.

Keep separate queues for unfilled values, stable local proofs, and global proof debt. A task's readiness is determined by its actual dependencies, not a single global ``all values first'' rule. Instance goals deserve special treatment because they may determine type variables and runtime operations; they are not merely proof debt. The existing rotation mechanism is a useful fallback, but its coarse classification should not become the whole scheduling semantics \cite{searchcore}.

\Q{R6.2}{Which properties follow by induction, simplification, and arithmetic?}
\ans An important sufficient class is characterized by a locally checkable invariant preserved by the program algebra. Membership in a selected \emph{certificate grammar} can be recognized. There is no reason to promise a syntactic test recognizing every theorem that an unrestricted induction tactic could eventually prove.

Let a structurally recursive program on $D=\mu F$ have algebra $a:F(K)\to K$. Let $I(x,r)$ describe the desired relationship between input subtree $x$ and result $r$. For each constructor $c$ with recursive children $x_1,\ldots,x_m$, require a branch certificate
\[
 \left(\bigwedge_{j=1}^{m} I(x_j,r_j)\right)
 \Longrightarrow
 I\bigl(c(\vec v,\vec x),a_c(\vec v,\vec r)\bigr). \tag{2}
\]
Nonrecursive fields $\vec v$ and ordinary hypotheses are universally quantified. Base constructors are the $m=0$ case.

\begin{theorem}[Algebraic invariant lifting]
If every constructor has a certificate of the form (2), then
$\forall x:D,\ I(x,\operatorname{fold}_a(x))$.
\end{theorem}
\begin{proof}
Induct structurally on $x$. For a constructor with children $x_j$, the induction hypotheses give $I(x_j,\operatorname{fold}_a(x_j))$. Instantiate (2) with these recursive results. The fold's computation equation identifies the resulting right-hand side with $I(x,\operatorname{fold}_a(x))$.
\end{proof}

This is the exact justification for synthesizing a value and proof together. For a dependent family, replace $K$ and $I$ by the appropriately indexed motive and carry the transport obligations explicitly. For a parameterized accumulator, quantify the parameter in the induction hypothesis whenever recursive calls change it.

A recognizable first proof class allows constructor equations, projections, equality congruence, fixed terminating simplification rules, and arithmetic obligations in a chosen decidable linear fragment. The recognizer checks that each generated branch obligation belongs to this fragment. Then a complete solver for that fragment can discharge it; otherwise the problem goes to the heuristic portfolio rather than being declared false.

For vector or list map, the length invariant reduces in the constructor branch from $|r|=|xs|$ to $1+|r|=1+|xs|$. That is a local arithmetic closure. Reverse involution often needs an append or accumulator lemma. Sorting needs a permutation and order invariant that is stronger than a few closed sortedness examples. Properties involving nested uses such as $f(f(x))=x$ may require an auxiliary theorem relating the second invocation to the first; the program's recursion alone does not make the proof local.

The practical recognizer should therefore report one of three things: a local certificate successfully checked, outside the current certificate grammar, or unresolved within its resource budget. It should never use the latter two as logical evidence that the candidate lacks the property.

\Q{R6.3}{Which automated-induction facilities are usable in Lean?}
\ans Start with the ordinary induction APIs and Lean's existing functional-induction support, then add bounded proof portfolios. Do not assume that a general-purpose solver discovers the necessary induction, generalization, and helper lemma automatically.

The pinned \code{v4.34.0} source implements the \code{fun_induction} tactic through the function \code{evalFunInduction}. It looks up a function's generated induction theorem, generalizes the selected targets, and passes the eliminator to the induction machinery. The same source has \code{fun_cases}. Thus the proposal's fallback can use an existing function-aligned induction facility once a candidate is published in a suitable equation-style form \cite{leanfuninduction}. Anonymous recursor terms may first need that publication step.

Use \code{simp}, \code{omega}, and \code{grind} as branch solvers with separately measured tiers. Aesop provides customizable proof search and is a useful optional library; custom induction rules may be registered, but that is different from general automatic induction discovery. Canonical supplies a more specialized optional comparison point. LeanHammer-style retrieval and proof search are another optional lane with external dependencies; none should be silently treated as part of a core-only installation \cite{aesop,canonical,leanhammer}.

The inspected evidence does not establish a production-ready, general Lean rippling-and-lemma-discovery service with guaranteed latency. That leaves a concrete engineering target: a bounded induction adapter that tries a short list of major premises and dependency-closed generalizations, simplifies using the candidate's equations, and invokes the existing branch portfolio. Record which substep consumed time so missing lemmas are not confused with failed induction-variable selection.

For time limits, restore the full tactic/metavariable state after failure and propagate cancellation distinctly. Heartbeats and recursion limits are useful accounting mechanisms, but a wall deadline checked only between search nodes does not preempt every long internal operation. The inspected engine sets the ambient heartbeat limit to zero and uses lane deadlines \cite{engine,transaction}. Expensive proof-service calls should receive their own resource limits; an external process is the strongest isolation option for an optional heavyweight service.

\Q{R6.4}{Is there a principled proof-debt schedule?}
\ans There is a useful elementary principle for a simplified model, but not a universal optimal bandit policy for the actual coupled search. Separate a justified ordering heuristic from the empirical model supplying its probabilities.

Suppose independent proof jobs $i$ and $j$ have fixed positive costs $t_i,t_j$ and success probabilities $p_i,p_j$, and the process stops at the first success. Trying $i$ before $j$ has expected charged time $t_i+(1-p_i)t_j$; the reverse order has $t_j+(1-p_j)t_i$. Therefore $i$ should precede $j$ precisely when
\[
  \frac{p_i}{t_i}\geq\frac{p_j}{t_j}.
\]
This exchange argument extends to an ordered list under the same assumptions. It motivates ``probability of useful success per unit cost,'' not an optimality claim for all proof debt.

Leant2 violates several assumptions: obligations share information, proofs can be prerequisites for other proofs, a successful local lemma can help many candidates, jobs can be resumed, and a failed tier changes the next tier's probability. Replacing this with independent arms of an ordinary bandit hides the dependency structure. Even a calibrated probability is conditional on the tactic tier, obligation shape, available lemmas, and previous failures.

A defensible default is deterministic and simple. Reject candidates using cheap confirmed counterexamples first. Attempt stable local obligations before global ones. Give each ready proof task a geometrically increasing resource ladder, record its progress, and reserve a fixed logical share for older pending tasks so they cannot starve. Learn probabilities only as an optional ordering layer over this fair schedule. Treat switching and setup costs explicitly when a service initializes an index or external solver.

The experimental objective should be time to \emph{certified} answer, together with the number and age of unproved survivors. A policy that returns many plausible programs quickly but spends no time proving the right one is not an improvement for this tool. The useful comparison is against fixed tiers and round-robin resumption, not an unsupported assertion that a particular bandit algorithm is optimal.
