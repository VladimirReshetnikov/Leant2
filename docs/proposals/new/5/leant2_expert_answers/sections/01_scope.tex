\subsection{How to read the claims}

Four kinds of claim are deliberately distinguished. An \emph{established result} is attributed to literature or inspected implementation. A \emph{derived result} is proved in this article, usually as a small mathematical statement that clarifies the design. A \emph{design recommendation} proposes an implementation and states its obligations; it is not presented as already implemented. An \emph{empirical question} is answered with a measurement protocol when the available evidence does not justify a numerical answer.

This is especially important for ``complete,'' ``minimal,'' and ``verified.'' Completeness can be relative to a specified grammar and a terminating decision procedure, or it can mean eventual discovery by fair unbounded enumeration. Neither means that an arbitrary time-limited run decides all Lean inhabitation problems. Minimality requires a fixed ordering and a named space of alternatives. Verification proves the submitted contract, which may be only a finite conjunction of examples; it does not discover or certify an unstated intention.

\subsection{The existing evidence supports a targeted rewrite}

The proposal reports 278/278 baseline cases and 350/350 signature-corpus cases, but thirteen unscored Church-operation stretch cases remain unresolved. Its edge probes expose missing comparisons and conditionals, unavailable dependent motives, a compilation problem for an accepted recursor term, and insufficient library retrieval. In one historical contract-heavy profile, residual evaluation accounts for 45\% of time, while state save/restore accounts for about 1\%. These numbers justify studying residual work and search branching before assuming that copying state is the principal cost. They are observations on the proposal's workload, not universal performance laws.\cite{evidence}

There is an important consequence for project order. It is unnecessary to solve unrestricted carrier invention before making progress. A bounded carrier grammar, sketches, and a finite observational constraint solver can be delivered while a fair general enumeration lane remains available. Likewise, a complete rewrite of Lean's evaluator is unnecessary before splitting observations and implementing correct dependency-based invalidation. The first useful milestones should have sharply delimited semantics and independently testable failure modes.
